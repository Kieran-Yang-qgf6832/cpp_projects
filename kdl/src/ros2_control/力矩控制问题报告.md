## 1. 问题一：教学库重力补偿符号写反

### 1.1 现象
按 `kdl_dynparam.hpp` 的注释实现重力补偿 ——「把 G(q) 取负号就是重力补偿力矩，控制器输出
`τ = −G(q)`」——会把重力**加倍**，机械臂会朝重力方向加速砸下去。
`example/dynamics_demo.cpp` 第 7 步的 `torque_cmd(i) = -g0.torque(i);` 是同一个错误。

（该错误在原来的 demo 里没暴露：第 7 步又在 joint1 上加了 `+2 N·m`，且只打印 joint1，
掩盖了"补偿方向错了"的事实。）

### 1.2 可能原因与排查过程
怀疑点在 KDL 的重力符号约定。**不靠注释、靠实测**，构造一个物理上无可争议的一维摆：

- 链：单段，`RotY` 关节在原点，质量 1 kg 的质心在 `(1, 0, 0)`（即 +x 方向）；
- 重力 `(0, 0, -9.81)`；
- 物理事实：质心在 +x，重力沿 −z ⇒ 关节受到 **+y 方向** 的重力矩 ⇒ 无驱动力矩时应向 +q 加速。

实测结果（`kdl` 直接调用，不经过本工程封装）：

```
ID  static   tau = -9.810000      ← inverseDynamics(q,0,0)
Gravity      tau = -9.810000      ← gravityTorque(q)
FD(tau=0)    qdd = +9.800200      ← 无驱动力矩确实自由下落（+q）
FD(tau=+Lmg) qdd = +19.600400     ← 加倍重力
FD(tau=-Lmg) qdd = +0.000000      ← 这才是"抵住重力"
```

结论：**`inverseDynamics(chain,q,0,0)` 与 `gravityTorque(chain,q)` 返回的就是"执行器为抵住
重力所需施加的力矩"，直接施加 `τ = +G(q)` 才对，不能取负。**

再用整机复核（与 MuJoCo 对照，见问题四的排查手段）：
在 `q = [0,-0.6,0.8,0,0.2,0]` 处
```
KDL inverseDynamics(q,0,0) = [0, +12.0628, -6.2376, +0.5567, -0.0044, 0]
MuJoCo qfrc_bias(q)        = [0, +12.0628, -6.2376, +0.5567, -0.0044, 0]
```
逐位一致 —— 两侧同号，进一步确认符号。

### 1.3 解决方案
- `src/Dynamics/include/kdl_dynparam.hpp`：把 `gravityTorque` 的 `@note` 从
  「取负号才是补偿力矩」改为「**返回值本身就是补偿力矩**，直接施加 `τ = +G(q)`，不要取负」，
  并写明与 `inverseDynamics(q,0,0)` 同号同值、可互相印证。
- `example/dynamics_demo.cpp`：
  - 演示列表第 6 项措辞更正；
  - 第 6 步输出文案更正；
  - 第 7 步符号 `-g0.torque(i)` → `g0.torque(i)`，并补上"不要取负"的注释。
- `src/ros2_control/include/kdl_effort_controller.hpp`：把"库里有 bug"的提醒改为"已一并修正"。

全仓 grep `gravityTorque` 复核了其余用法：`example/control_demo.cpp` 只是拿它做量级对照
（未取负），无需改动。

### 1.4 是否解决及效果
**已根治。** 控制器统一使用 `kdl_dynamics::inverseDynamics(...)`（执行中用轨迹点、
空闲时用 `inverseDynamics(q_ref,0,0)`），符号正确；端到端悬停与跟踪均正常。

### 1.5 后续
无。建议在 review 时留意"把注释当规格"的风险。

## 2. 问题二：`mujoco_pids.yaml` 原始 PID 在本力矩环中不可用

### 2.1 现象
按需求「kp/kd/ki 使用 `mujoco_pids.yaml` 的值」原样使用（`p=100..300`、`d=20..40`、
`u_clamp=±50/±100`）时，机械臂在闭环里**大幅摆动**：关节速度冲到 80+ rad/s、力矩长期饱和
（`effort[0]=50.0`），完全锁不住。

### 2.2 可能原因与排查过程
1. **判断是否饱和**：`u_clamp=±50`，`kp=300`（joint2）⇒ 线性区只有 `50/300 ≈ 0.17 rad`。
   只要位置误差超过 0.17 rad，PD 两项就同时饱和 → 退化成 bang-bang（±50 来回打），
   阻尼项失效 → 极限环。
2. **量化被控对象的等效惯量**：用 MuJoCo 打印关节空间惯性矩阵对角 `M(q)`：
   ```
   q=0 : 0.00696  1.47550  0.33111  0.00786  0.00159  0.00011
   q=A : 0.49756  1.36075  0.32462  0.00773  0.00159  0.00011
   ```
   joint2 的等效惯量 ≈ 1.4 kg·m²，joint6 只有 ≈ 1.1e-4 kg·m² —— 两者相差 4 个数量级，
   一套"看起来差不多"的经验增益不可能同时合适。

### 2.3 解决方案
按标准二阶闭环反推（`kp = M·ωn²`，`kd = 2ζM·ωn`），取 `ωn = 15 rad/s`、`ζ = 1`（临界阻尼），
惯量取"该关节在常见位形下的较大值"以保证稳定：

| 关节 | M(q) 量级 | kp | kd |
|---|---|---|---|
| joint1 | 0.007 ~ 0.50 | 110 | 15 |
| joint2 | 1.36 ~ 1.48 | 300 | 40 |
| joint3 | 0.32 ~ 0.33 | 70 | 10 |
| joint4 | 0.0078 | 2.0 | 0.25 |
| joint5 | 0.0016 | 0.4 | 0.05 |
| joint6 | 0.00011 | 0.3 | 0.03 |

`i` 全部保持 0（前馈 τ_ff 已把重力准确抵消，不需要积分消差，见问题四）。`u_clamp` 不变。

### 2.4 是否解决及效果
**已解决（对当前机型）。** 最大偏差收敛到 < 1e-4 rad；`τ_pid` 基本在零点附近微调，
不再饱和。

### 2.5 后续
- 换了机型（惯量变化）必须重算这组增益；
- 若想更"硬"的跟踪，可提高 `ωn`，但要同步检查 `u_clamp` 是否够用；
- 该文件现在是**力矩环的增益来源**，其文件头的注释（原本写给"插件内部位置 PID"）已过时，
  实现时已在 `controllers.yaml` 与控制器注释里指明真实用途。

## 3. 问题三：控制器激活前的自由下落（**未根治**）

### 3.1 现象
`kdl_effort_controller` 被 spawner 激活之前，`ctrl=0`（MuJoCo 对 `<motor>` 的初值），
机械臂在重力下**自由下落**；等到控制器接手时，臂已经砸到关节限位并带着很大速度，
闭环一接手就发散（实测 joint1 速度冲到 82 rad/s、力矩饱和、在 ±限位之间大幅摆动）。

有时能正常悬停、有时发散，**取决于 spawner 的启动时序**（随机性很强）。

### 3.2 可能原因与排查过程
1. 打印日志时间线：
   ```
   575.950  MujocoSystemInterface: Using MuJoCo motor or custom actuator ...（硬件注册）
   577.370  Joint joint1: effort control enabled ...（控制器激活，effort 接口被 claim）
   ```
   即从物理开始步进到控制器真正出力之间，有 **≈1.4 s 的"无控制"窗口**。
2. 打印控制器**首帧**状态，发现它接手时 `q` 已经等于限位值（`[-0.31, 1.57, 2.80, -1.13, ...]`）——
   证实"接手前就已经掉到底"。
3. 确认 `mujoco_ros2_control` **没有"启动即暂停"的参数**（只有运行期 `~/set_pause` 服务）。

### 3.3 解决方案（缓解）
给 `src/model/robotic_arm_torque.xml` 的各关节加**粘性阻尼** `damping`，把下落速度压住：

| 关节 | damping | 说明 |
|---|---|---|
| joint1 | 2.0 | 基本不受重力矩，给一点即可 |
| joint2 | 25.0 | 承重最大（τ_g ≈ 12 N·m） |
| joint3 | 18.0 | τ_g ≈ 6 N·m |
| joint4 | 0.3 | 手腕关节惯量小，阻尼不能大 |
| joint5 | 0.05 | 同上（J ≈ 1.6e-3） |
| joint6 | 0.05 | 同上（J ≈ 1.1e-4）。原模型是 2.0，会像"锁死" |

> 关键取舍：阻尼要按 `J/c`（时间常数）配。手腕关节的 J 极小，若沿用躯干的阻尼量级
> （如 joint6 原本的 `damping=2.0`），阻尼力矩会远超 PD，关节几乎动不了、跟踪严重滞后。
> 第一版给 joint4/5/6 分别加了 5.0/2.0/0.05，结果 j6 几乎不动 —— 这就是 `J/c` 没配平。

### 3.4 是否解决及效果
**缓解，未根治。** 多数运行下 t=16 s 时臂已**完全静止悬停**（各关节速度 ~1e-9），
端到端精度 < 1e-4 rad。但"落到底概率"仍受 spawner 时序影响：
`colcon build` 后首次启动、或机器负载高时，spawner 更慢，仍可能失稳。

### 3.5 后续如何彻底解决（按可行性排序）
1. **启动即暂停**：在 launch 里让仿真先暂停 → 等 `joint_state_broadcaster` 与
   `kdl_effort_controller` 都 active → 再 `~/set_pause{paused:false}`。
   现状 `mujoco_ros2_control` 无法在启动时暂停，需要：
   - 方案 a：给它的 `<hardware>` 加一个 `start_paused` 参数（改上游或本地 vendored 源码）；
   - 方案 b：launch 里在 `ros2_control_node` 起来后立刻调用 `~/set_pause`（有竞争，不够稳）。
2. **写一个 `mujoco_ros2_control_plugins` 插件**：在控制器接手前对 `data->ctrl[]` 施加
   `G(q)`（需要模型惯量信息），等控制器 active 后让位。最干净但工作量最大。
3. **提高"控制器早于物理"的把握**：把握 spawner 时机不可靠，只能作为辅助。
4. **接受现状并加保护**：控制器激活时若检测到 `|q̇|` 过大，先进入"刹车 + 重力补偿"
   模式（只给 `τ = G(q) − kd_brake·q̇`），速度降下来再切正常 PD。这是纯软件、可立即做。

## 4. 问题四：j4 稳态偏差 0.35 rad（本以为是控制问题，实为假自碰撞）

### 4.1 现象
闭环稳定后，j1/j2/j3/j6 都能到目标，**唯独 j4 恒定停在离目标约 0.35 rad 处**
（目标 0.30，停在 −0.05）。现象很"像"控制问题：静差、且不同目标下残留不同。

### 4.2 可能原因与排查过程
按"先排除控制、再怀疑模型"的顺序，逐条排除：

**(a) 前馈符号/数值？排除。** 用 MuJoCo 打印同一构型下的重力项与 KDL 对照：
```
目标构型 A: MuJoCo qfrc_bias = [0, +9.1008, -5.1469, +0.2915, -0.0285, 0]
            控制器 τ_ff      = [0, +9.1,    -5.1,    +0.3,    -0.0,    0]   ✅ 吻合
```

**(b) ROS 命令链路？排除。** 把**同一控制律**在纯 MuJoCo 里离线复现（不经过任何 ROS 话题/接口）：
```
闭环 50 s 后 q = [0.50000, -0.40059, +0.60245, -0.05011, +0.16803, +0.50000]
```
与 ROS 在线运行结果**完全相同** —— 说明命令确实到达了仿真，问题不在链路上。

**(c) 增益太小？排除。** 加大 kp 只是让误差变小、不改变"停在中途"这一事实；
且 j1/j2/j3/j6 用同样的逻辑都能到位。

**(d) 直接量力矩平衡（关键一步）。** 打印末态各力的分解：
```
ctrl           = [0, +9.27822, -5.31850, +0.99172, -0.01571, 0]   ← 控制器施加
qfrc_actuator  = [0, +9.27822, -5.31850, +0.99172, -0.01571, 0]   ← 实际施加（与 ctrl 一致）
qfrc_bias      = [0, +9.27822, -5.31850, +0.45372, -0.01489, 0]   ← 需要抵住的广义力
qfrc_constraint= [0, 0,        0,        -0.53800, +0.00082, 0]   ← ***约束力***
qacc           = 0
```
`qfrc_constraint[3] = −0.53800` **恰好**抵消 j4 的净力矩（0.99172 − 0.45372 = 0.538）。
其余关节的 `qfrc_constraint` 都是 0 —— **只有 j4 被"某种约束"顶住了。**

**(e) 是什么约束？** 打印接触列表：
```
ncon=1
contact 0: link3 <-> link5   dist = -0.00111
```
**是 link3 与 link5 的自碰撞**（穿模 1.1 mm）。

**(f) 验证。** 在离线复现里关掉接触（`mjDSBL_CONTACT`）后：
```
[disable contact] q = [+0.5000, -0.4000, +0.6000, +0.3000, +0.2000, +0.5000]
qref              = [+0.5000, -0.4000, +0.6000, +0.3000, +0.2000, +0.5000]   ✅ 精确到达
```

### 4.3 原因
本模型的连杆碰撞直接用 SolidWorks 导出的三角网格，**MuJoCo 对非凸网格用凸包近似**，
会把实际仍有间隙的连杆误判成接触。`<motor>` 力矩模式下没有位置伺服"硬顶"过去，
这个假接触产生的约束力会长时间把关节顶在半路，表现为"关节无论如何到不了目标"。

（同一个假接触在原来的 `<position>` 位置伺服下也存在，只是被位置伺服的"硬顶"掩盖，
或者因为目标不同没有触发。）

### 4.4 解决方案
在 `src/model/robotic_arm_torque.xml` 的 `<contact>` 里，**把非相邻连杆两两 exclude**
（相邻连杆本来就已 exclude）：
```
base_link×{link2..link6}、link1×{link3..link6}、link2×{link4..link6}、
link3×{link5,link6}、link4×link6
```
并在注释里写明：这是为了规避凸包假接触；若要保留真实自碰撞检测，应删掉这些 exclude，
并把连杆的 `geom` 换成简化碰撞几何（capsule/box），而不是用外形网格。

### 4.5 是否解决及效果
**已解决。** 修完后 j4 精确到位。端到端实测两个目标：
```
A 目标 [0.5,-0.4,0.6,0.3,0.2,0.5] → 实际 [0.49999,-0.39999,0.59994,0.30006,0.20004,0.49999]
B 目标 [0.2,-0.3,0.4,0.1,0.1,0.2] → 实际 [0.20000,-0.30000,0.40001,0.09998,0.09999,0.20000]
```
max 残差 < 1e-4 rad。

### 4.6 后续
- 若后续要演示"自碰撞避让"，必须补简化碰撞几何，不能直接删 exclude；
- 排查手法可复用：**"净力矩不为零却不加速" ⇒ 立刻打印 `qfrc_constraint` 与 `ncon`**，
  而不是继续调控制器增益。

## 5. 问题五：完成判据只看时间，不看是否到位

### 5.1 现象
在问题四还没定位时，j4 实际差了 0.35 rad，但 service 仍返回
`error_code=0, success=true, message='执行完成'`。调用者会误以为任务成功。

### 5.2 可能原因与排查过程
控制器的状态机以"参考时间 `elapsed ≥ duration`"判定结束（这是 `PLAN_TORQUE.md` §6.3 的设计），
**没有任何跟踪精度判据**。于是"参考跑完"和"机械臂到位"被当成一回事——被障碍/限位/限幅卡住时
也会报成功。

### 5.3 解决方案
在 `kdl_control_node` 的 service 尾部加**终点到位自检**：
1. 控制器报 `active:false` 后，**轮询等机械臂真正停下来**（各关节 `|q̇| < 0.05 rad/s`，
   最多等 3 s，墙钟）；
2. 取轨迹末点作为期望，与当前 `/joint_states` 比对，取各关节最大绝对残差；
3. 残差 > `tracking_tolerance`（新参数，默认 0.05 rad）→ 返回新错误码
   **`error_code = 8`（轨迹时间跑完但未到位）**，message 说明是哪个关节差多少、常见原因。

> 注意：一开始用的是"固定 0.5 s 后测量"，结果**误报**——低增益的手腕关节（j6）收尾很慢，
> 0.5 s 时还差 0.053 rad，而它最终会收敛到 0.007 rad。所以必须**等停稳再量**。

同时把 `ControlTask.srv` 的错误码注释补全（新增 8），并把其中过时的 "arm_controller/JTC"
描述改成新的力矩控制器链路。

### 5.4 是否解决及效果
**已解决。** 现在的行为：
- 正常到位 → `error_code=0`（实测 A/B 两个目标都是 0）；
- 未到位（如被自碰撞卡住）→ `error_code=8` + 明确到关节的残差信息。

### 5.5 后续
- `tracking_tolerance` 默认 0.05 rad 偏松，可按机型收紧到 0.01 rad；
- 若将来要区分"因为接触卡住"和"因为力矩限幅"，可在控制器里额外回报饱和标志，
  让错误信息更精确（当前靠 message 里的常见原因提示）。

## 6. 与 `PLAN_TORQUE.md` 的偏差（实现记录）

| 项 | 计划 | 实现 | 原因 |
|---|---|---|---|
| 空闲重力前馈 | `gravityTorque(chain, q_meas)` | `inverseDynamics(chain, q_ref, 0, 0)` | ① 用 `q_ref`（setpoint gravity comp）才能零静差；② 与执行态的 τ_ff 用同一函数，符号天然一致 |

## 附录 A：本次排查用到的手段（可复用）

1. **一维摆判据**：用一个质心明确、重力方向明确的单关节链，把"符号约定"变成"能不能抵住"的
   二元事实（`FD(τ)` 是否为 0）。
2. **KDL ↔ MuJoCo 交叉验证**：`inverseDynamics(chain,q,0,0)` 对 `mjData.qfrc_bias(q)`，
   逐位比对，判断前馈是否可信。
3. **离线复现控制律**：把 ROS 控制器里的同一段控制律写进一个纯 MuJoCo 小程序，若结果与在线
   一致，即可**排除 ROS 链路**；再在离线程序里关掉接触、改初值，快速二分定位。
4. **力分解对照**：同时打印 `ctrl` / `qfrc_actuator` / `qfrc_bias` / `qfrc_passive` /
   `qfrc_constraint` / `qacc` —— "净力不为零却不动"必然对应非零的约束力。
5. **读 `M(q)` 对角**：调增益前先量等效惯量，避免用"经验值"跨 4 个数量级去猜。
6. **接触列表**：`ncon` + 接触对 + `dist`，确认是不是几何/碰撞问题。
